# Module 2: Designing and Deploying Agentic Systems

**Author:** Alexander Booth
**Date:** May 2026
**Cohort:** MIT-AGAI April 27, 2026

## Overview

Module 2 is the **implement** module of the program: it moves learners from understanding what agentic AI is to understanding how it is actually built, orchestrated, and rolled out inside an organization. MIT's Jacob Andreas opens the module by extending the agent architecture from Module 1 with **memory and learning**, then walks through the failure modes — agent mistakes and user manipulation — that make external safeguards non-negotiable, before closing on multi-agent systems and multimodal/physical-world agents. The module then shifts from architecture to leadership practice: a Google Cloud AI practitioner discusses build-vs-buy-vs-stack decisions, human-in-the-loop governance, and 6–12 month planning; an AI platform founder walks through real client workflows, task decomposition, and where pilots die on the way to production; and a narrative podcast dramatizes an executive team designing its first agentic deployment end to end. Across all four units, the same five architectural decisions — **perception, action, planning, memory, and safety** — recur as the vocabulary for talking about any agent, regardless of who is speaking or what industry they're in.

## Why This Module Matters

Module 1 established that agentic AI is a distinct category — systems that plan, use tools, and act rather than simply respond. That distinction is only useful once leaders can answer the next question: what actually has to be built, bought, or governed to make an agent trustworthy in production? Module 2 answers that question by showing that **the difference between a language model and an agent is not scale, but scaffolding** — memory architectures, safeguards that sit outside the model, orchestration across subagents, and human-approval thresholds calibrated to risk. This is also where the program's abstractions get tested against practice: two industry conversations and a full narrative case study show that the same five building blocks Andreas introduces in the lesson are exactly what a real executive team has to decide on a whiteboard before it can ship anything. Module 3 will build on this by asking how to govern and scale what gets designed here — so getting the architecture and the first-deployment discipline right in Module 2 is what makes scaling in Module 3 a matter of governance rather than a rebuild.

## What This Module Covers

1. **Memory and learning turn a one-off interaction into a reusable capability.** Without memory, an agent re-derives the same reasoning for every user, every time. Andreas distinguishes three forms of learning: **user memory** (profiles that personalize future interactions), **procedural memory** (caching successful workflows so the agent doesn't recompute them), and **model-level learning** (using aggregated interaction data to update the model's weights, typically via reinforcement learning run by model providers, not end users). The design challenge is not storing everything — it's selectively capturing what's useful in a compressed, shareable, and appropriately anonymized form.

2. **Agents fail in two directions, and the fix is architectural, not behavioral.** Language models are structurally unpredictable: they hallucinate, execute flawed logic, or take consequential actions (like processing a return) without surfacing them to the user first. Separately, users can manipulate agents through malicious prompting to extract discounts or trigger unauthorized actions. In both cases, the model itself cannot be trusted to manage the risk. Safeguards — explicit human approval for consequential actions, hard-coded confirmation steps that never pass through a language model, monitoring systems that flag high-risk behavior, and privacy rules that only expose information a user has already proven they're entitled to — have to live in the surrounding system, not in the model's judgment.

3. **Multi-agent systems and multimodality extend the same five fundamentals rather than replacing them.** Most multi-agent systems are best understood as a single agent whose planning is distributed across subagents coordinated by a controller — except in distributed organizations, where each user's agent must independently decide what information to share on a user's behalf, raising real coordination and access questions. Multimodal agents (image input/output, code that drives robots) extend agents beyond text, but the best of these systems still hand off to lower-level, specially trained controllers for fine-grained perception and manipulation — the frontier is expanding, but agent design still reduces to **observation, action, planning, memory, and safety**.

4. **Build, buy, or stack is a leadership decision driven by autonomy and skill, not a technology choice.** There's no universally correct answer to whether an organization builds its own agent stack, buys a platform, or assembles components from multiple vendors — it depends on the autonomy the organization wants, whether it has the skills to support what it builds, and whether the capability belongs in its core business. Most enterprises end up doing a combination of all three, and vendor lock-in is a real cost of the "buy" path that has to be weighed deliberately.

5. **Human-in-the-loop is a set of thresholds, not a single switch, and evaluation has to be continuous.** At this point in the technology's maturity, full autonomy and regulated industries don't yet coexist — human-in-the-loop remains a must, calibrated through thresholds (e.g., ignore small-dollar fraud, escalate everything else). The discipline that supports this at scale is what practitioners are calling **AgentOps**: continuous evaluation of outcomes for skew, built into the deployment architecture itself, rather than a one-time pre-launch test — because a model or version upgrade can silently break a previously working system.

6. **Task decomposition is the core design skill for turning a methodology into a workflow.** The heuristics for when to decompose a task into multiple agentic steps: you're repeating the same prompt sequence, the model's output stays flat despite good prompting (a signal the model or data is too complex for one step), or the task exceeds what a model can hold at once (e.g., reviewing a 200-page contract). Consistency in an inherently inconsistent medium is engineered the same way you'd manage inconsistency in people: simplify the task, give examples (few-shot/multi-shot), use self-consistency (ask multiple times, take the average), and validate outputs — especially by having a second model check the first model's references to reduce hallucination.

7. **Pilots die in the people, not the infrastructure.** Most organizations get the infrastructure — data access, secure and scalable APIs — right by default. What kills agentic initiatives on the way from prototype to production is change management: if the people who will use an agent don't help generate the idea for it, or perceive it as a threat, they resist it and reject its output regardless of quality. The organizations that succeed invest early in structured use-case discovery (since a small fraction of use cases deliver most of the value), treat their agent initiatives as a portfolio to be pruned aggressively, and put subject-matter experts who are AI-enthusiastic — not engineers — in charge of building workflows.

8. **Every agent needs a manager.** As deployments scale, "human-in-the-loop" stops being an abstract principle and becomes an org-chart question: who owns the judgment of whether an agent's decisions are still good, who notices drift, and who intervenes? That role sits closer to the business function the agent serves (e.g., procurement) than to engineering, and most organizations haven't yet created it — it has to be grown, not simply staffed.

* **U4 — Podcast** (`MIT AGAI M2U4 Podcast 1 Transcript.pdf`): a narrative teaching case (fictional company, "Boulton Industries") dramatizing an executive team's second design meeting for its first agentic deployment. The team evaluates five candidate use cases and deliberately selects the one — supplier qualification and onboarding — that will force the most architectural decisions, not the easiest win. The CTO frames the choice using Herbert Simon's concept of **bounded rationality** ("bounded on purpose"), then walks the team through the same **five building blocks** from the lesson (perception, action, planning, memory, safety) as concrete architectural decisions rather than features. The team debates build vs. buy vs. stack (choosing a decoupled stack), sets a disciplined three-week MVP scoped tightly enough to make that speed safe, defines human-in-the-loop as a **threshold map** rather than a single switch, adopts continuous evaluation (**AgentOps**) as a live, monthly-reviewed discipline, and concludes that **every agent needs a manager** — a new organizational role, not an engineering add-on.

## Key Takeaways

* The difference between a language model and an agent is **scaffolding, not scale** — memory, tools, orchestration, and safety constraints are what turn text generation into reliable action.
* **Safeguards must live outside the model.** You cannot rely on a language model to police its own mistakes or resist manipulation; human approval, hard-coded confirmation steps, and monitoring systems have to sit in the surrounding architecture.
* **Build, buy, or stack is a leadership decision** shaped by desired autonomy and existing skill, not a purely technical one — and most enterprises end up combining all three rather than picking a single path.
* **Human-in-the-loop is a set of calibrated thresholds**, not a binary switch, and evaluation has to be continuous (AgentOps) because a model upgrade or drift can silently break a working system.
* **Task decomposition is the core design skill**: decompose when you're repeating prompt sequences, when output stays flat despite good prompting, or when a task exceeds what one model call can reliably hold.
* **Pilots die on the people side, not the infrastructure side** — successful deployment requires disciplined use-case discovery, portfolio-style pruning of what doesn't work, and a newly defined "agent manager" role to own ongoing judgment about whether an agent is still performing as intended.
